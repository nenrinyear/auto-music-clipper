# 演奏録音の自動トリミング — 詳細仕様 v0.2

更新日: 2026-09-27

この文書は実装する動作とインターフェースの仕様案。ユーザー確認済みの要件、採用する設計案、実録音によって調整する検出パラメーターを区別する。処理精度・速度・メモリ量は未測定。

## 1. 目的と確認済みの要件

- 吹奏楽・アンサンブルの録音を扱う。
- 入力は48,000 Hz・IEEE 754の32 bit float音声。初版のファイル形式はWAVとする。
- 初版は1ファイル1曲。1曲に複数の楽章が含まれていてよい。
- 最初の演奏音の約1秒前から、最後の余韻が自然に消える位置、または終演後の拍手が始まる直前までを残す。
- ステレオの左右には同じ固定倍率をかけ、左右の音量バランスを保ってノーマライズする。
- Rustで処理を実装し、WASMとしてCloudflare Workersから利用する。
- まずRustの解析・トリミングを作る。Cloudflareのリソース作成やデプロイは後工程で、ユーザーが予定している公式connectorを使う。

複数曲を含む録音は将来の対応範囲。初版へ入力された場合も内部区間を勝手に削除せず、最初から最後までを1つの作品として扱う。

## 2. 編集の原則と複数楽章

1. 作品全体の冒頭と末尾だけを切る。
2. 途中の休符、楽章間の無音、楽章間の拍手をそのまま保持する。
3. 曲全体を通して左右共通のゲインを1つだけ適用し、楽章ごとの強弱を保つ。
4. 自動判定の候補と、実際に書き出す編集計画を分ける。
5. 判定が曖昧なときは候補と理由を示し、境界の確認を必要とする。
6. 入力ファイルは変更せず、新しいファイルへ出力する。

```text
準備音・暗騒音 | 第1楽章 | 長い休止・拍手 | 第2楽章 | 余韻 | 最終拍手
          ↑ 開始1秒前                                 ↑ 終了候補
          └──────────────── 残す範囲 ──────────────────┘
```

「その後に演奏があるか」はファイル全体の解析後に判断する。何秒静かになっても、それだけで作品の終了とはしない。初版では楽章数の入力を求めない。

最初の有力な演奏候補から最後の有力な演奏候補までを包む範囲を作品とする。途中の拍手後に弱い演奏候補がある場合、前の楽章で自動終了せず、後続楽章の可能性を評価する。確信が足りなければ `possible_later_music` として確認を求める。

2秒以上の休止を `possible_break` として返す。ただしこれは表示用の暫定閾値で、終了判定には使わない。楽章と長い休符を音声だけから常に区別できるとは想定しない。正式な楽章境界・楽章数・楽章名は確定せず、休止の検出精度に依存しないで内部を保持する。

音が途切れず続く楽章は1つの連続区間になってよい。終演後の調律・舞台上の片付け・会話・別の音楽は誤認要因になるため、有力な演奏候補が競合するときは確認を求める。

## 3. 入出力フォーマット

### 3.1 入力

| 項目 | 初版の仕様 |
| --- | --- |
| コンテナ | RIFF/WAVE、little endian |
| サンプルレート | 48,000 Hzのみ |
| サンプル形式 | IEEE float 32 bitのみ。32 bit整数PCMは対象外 |
| WAV形式識別 | WAVE_FORMAT_IEEE_FLOAT、またはWAVE_FORMAT_EXTENSIBLEのIEEE_FLOAT subformat |
| チャンネル | モノラルまたはステレオ。主対象はステレオ |
| 配列順序 | ステレオはL,Rのinterleaved。順序を変更しない |
| 長さ | ローカル版は最大120分を設計上限とする。性能保証値ではない |
| dataチャンク | 初版は1つ。重複data、圧縮WAV、RF64/BW64/WAVE64は未対応エラー |
| メタデータ | fmt/data以外のチャンクがあっても、サイズとパディングを検証して読み飛ばす |

拡張子だけで形式を決めず、ヘッダーを検査する。fmtはdataより前に必要とする。block align、byte rate、data長、実ファイル長の整合性を確認し、途中で切れたデータ、フレームの途中で終わるdata、不正チャンク長はエラーにする。

Extensibleのチャンネルマスクは、ステレオでは未指定またはFL/FR、モノラルでは未指定またはFCを受け入れる。それ以外の配置は未対応とする。コンテナのビット数と有効ビット数はともに32を要求する。

有限の値は絶対値が1を超えていても受け入れ、解析前に±1へクランプしない。NaN/±Infinityは位置とチャンネルを添えてエラーにする。0 dBFS超過と、録音時に波形が失われたクリッピングは同一視しない。

### 3.2 出力

- 標準出力は48,000 Hz・32 bit float WAV、入力と同じチャンネル数。
- fmt/fact/dataを生成し、data長とサンプルフレーム数を正しく記録する。
- 境界・設定・ゲイン・判定理由をJSONの別ファイルに保存する。
- 24 bit整数PCM、ディザ、圧縮形式への変換は後続機能とする。
- cue、ループ位置、BWF時刻等は切断後に不正確になるため、そのまま転記しない。入力メタデータがある場合は、引き継いでいないことを結果に記録する。
- 既存出力はデフォルトで上書きしない。入力と出力が同一ファイルになる指定は、上書き指定があっても拒否する。

## 4. 時刻と境界

基準単位はサンプルフレーム。ステレオの1フレームはLとRの2サンプルを含む。Rust内部はu64で管理し、秒表示は `frame / 48000` で計算する。最大120分のフレーム番号はJavaScriptの安全な整数範囲に収まる。

| フィールド | 意味 |
| --- | --- |
| `music_start_frame` | 作品の最初の演奏音の推定位置 |
| `last_music_end_frame` | 最後の新たな発音または持続した演奏から、余韻へ移る推定位置 |
| `tail_end_frame` | 最後の余韻が暗騒音に近づき、聴き取りにくくなる推定位置 |
| `final_applause_start_frame` | 最終演奏後の拍手の最初の立ち上がり。途中の拍手とは別 |
| `start_frame` | 出力に含む最初のフレーム |
| `end_frame` | 出力に含まない最初のフレーム |

出力区間は `[start_frame, end_frame)`、フレーム数は `end_frame - start_frame`。未知の時刻はnullとし、0やファイル末尾で代用しない。演奏と余韻の境目が曖昧でも、出力終了の十分な根拠があれば候補は提示できる。

## 5. トリミング規則

### 5.1 開始

```text
start_frame = max(0, music_start_frame - pre_roll_frames)
pre_roll_framesの既定値 = 48,000（1秒）
```

演奏候補の確定には前後の文脈を使い、確定した瞬間から切るのではなく最初の弱い立ち上がりまで戻る。息の音、弱音のソロ、単発の打楽器で始まる曲も評価対象にする。

咳や譜面の音だけで開始を決めない。前余白1秒に入る物音はそのまま残し、物音を避けるために余白を自動短縮しない。

録音が演奏中から始まっている疑いがある場合は0秒を候補として `start_truncated` を返す。前余白を確保できない場合は実際の余白長を示し、無音を合成して補わない。

### 5.2 終了

最終演奏区間を選んだ後、その終わりの余韻と拍手を評価する。

```text
natural_end = tail_end_frame + 9,600（0.2秒）
applause_limit = final_applause_start_frame - 2,400（0.05秒）
```

| 検出結果 | 終了候補と状態 |
| --- | --- |
| 余韻の終了が明瞭、拍手なし | natural_endをファイル末尾で上限処理 |
| 余韻が消えた後に拍手 | min(natural_end, applause_limit) |
| 余韻が残っている間に拍手 | applause_limitを候補にし、`tail_applause_overlap` で要確認 |
| 拍手は明瞭、余韻終了は不明 | applause_limitを候補にし、`tail_uncertain` で要確認 |
| 余韻終了は明瞭、曖昧な拍手候補が境界に影響 | 自然な終了と拍手前の候補を示し、`applause_uncertain` で要確認 |
| 末尾まで演奏または余韻が続く | 元の末尾を候補にし、`end_truncated` で要確認 |
| どちらも判定できない | 元の末尾を候補にし、`end_uncertain` で要確認 |

引き算は符号付きの一時値で計算し、範囲検査後にフレーム番号へ変換する。`0 <= start < end <= total_frames` を満たさない候補は無効とする。明確な演奏区間を切り落とす候補を自動採用しない。

拍手自体は余韻終了後でも、手前に取る余裕によって `applause_limit < tail_end_frame` になる場合は、余韻を短縮する要確認候補として扱う。

拍手前の50 msは拍手除去の保証ではなく初期値。立ち上がりの不確かさも結果に添える。余韻と拍手が重なった場合、トリミングだけで音源分離はできない。拍手前で切る案を提示し、余韻を優先して拍手を含める位置も手動で選べるようにする。

### 5.3 フェード

- 既定は開始5 ms、自然な終了50 ms、拍手直前で切る候補100 ms。
- 開始フェードは前余白の中に収まる場合だけ自動適用する。収まらない場合は0 msにして理由を返す。
- 終了フェードは切断位置から逆算する。明確な演奏本体にかかる場合は要確認。
- 録音が途中で終わった疑いがある場合、自動では終了フェードをかけない。手動指定は可能。
- 左右で同じカーブを使う。長さMのインは `sin(pi * i / (2 * (M - 1)))^2`、アウトは逆順（i=0..M-1）。
- M=0は無処理、M=1は不正設定。前後の合計フェード長が出力フレーム数を超える計画も拒否する。
- フェードはOFFにできる。内部の休止・楽章境界には追加しない。

## 6. ステレオ共通ノーマライズ

対象は最終的に保存する全区間。削除する前後の拍手は計測に含めない。保持する楽章間の拍手・物音は含め、出力全体のピークを管理する。

```text
p = max(abs(input_sample × fade))  // 全出力フレーム・全チャンネル
t = 10 ^ (target_peak_dbfs / 20)
g = min(t / p, 10 ^ (max_gain_db / 20))
output_sample = f32(f64(input_sample) × fade × g)
```

既定はON、目標 -1.0 dBFS、増幅上限 +18 dB。p>tなら減衰する。1を超える入力も切り捨てず、必要な倍率で減衰させる。累積・ピーク・倍率計算はf64を使い、最終出力でf32へ丸める。

| 状況 | 動作 |
| --- | --- |
| p=0 | g=1、無音フラグを返す。0除算しない |
| 必要な増幅量が上限を超える | 上限まで増幅し、`gain_limited` を返す |
| 演奏未検出または境界が未承認 | 自動書き出しをしない |
| ノーマライズOFF | g=1。1を超える有限値もfloat出力へ保持し、ピーク超過を表示 |
| NaN/Infinity | 書き出し前にエラー |

目標値はサンプルピーク。true peakや曲間のLUFS一致は保証しない。左右独立の正規化、左右差補正、コンプレッサー、リミッター、DC除去、ノイズ除去は初版に含めない。

入力全体の左右別ピーク、選択範囲のフェード後ピーク、共通ゲイン（倍率・dB）、丸め後の実出力ピーク、増幅上限に達したかを結果に記録する。JSONで無音のdB値を表すときはInfinityを出さず、nullと無音フラグを使う。

## 7. 解析アルゴリズムの初期設計

ここは実験を伴う部分。入出力と保護動作は固定し、検出ルール・係数は実録音で調整して `algorithm_version` を更新する。下記の特徴だけで常に楽器・拍手・会話を分類できるとは想定しない。

### 7.1 特徴抽出

- FFT窓2,048フレーム（約42.67 ms）、Hann窓。ホップ480フレーム（10 ms）。
- 左右を別々に計算し、RMSは平均パワーと片側最大値、スペクトルは左右のパワーを統合する。逆相キャンセルを避けるためL+Rの波形平均は使わない。
- RMS、ピーク、低域・中域・高域の相対エネルギー、spectral flux、spectral flatness、スペクトルの持続性、衝撃音の密度と反復性を候補特徴とする。
- 保存する特徴は1ホップあたり最大48 bytesを目標にする。スペクトル全体やPCMは全時間分保持しない。
- チャンク境界の窓は状態を持ち越す。最後の未完窓は解析用にゼロ埋めし、有効フレーム数を記録する。埋めた0を暗騒音・余韻終了の根拠に使わない。
- 特徴時刻は窓中心。サンプル座標への変換で窓のずれを補正し、候補周辺は再読込して細かく調べる。

spectral flatnessは音のノイズらしさ、spectral fluxはスペクトルの時間変化の手掛かりとして使う。単独で拍手を判定しない。周波数帯の区切り・特徴の重み・平滑化幅は、実録音で選定するアルゴリズム設定として版管理する。

### 7.2 暗騒音と候補生成

冒頭を無音と決めつけない。低エネルギーで比較的安定した区間を録音全体と境界付近から探して局所的な暗騒音を推定する。弱い演奏を暗騒音に含めないよう、音の持続性・周波数特徴も参照する。推定が成立しなければ `noise_floor_uncertain` にする。

実験開始用の値は、強い開始候補が暗騒音+10 dB、弱い立ち上がりへの逆探索が+3 dB、余韻終了の確認が暗騒音+3 dB付近で0.8秒継続とする。これらは補助条件で、短い最初の音や息の音を棄却する絶対条件にはしない。

開始と終了に別の条件を使い、閾値付近の揺れで状態が頻繁に変わるのを防ぐ。固定dBFSだけに依存せず、録音レベルが異なっても扱える相対特徴を使う。出力用ノーマライズの前に解析する。

### 7.3 ファイル全体を読んでから判断する

1. 演奏、余韻、拍手、暗騒音、その他・不明の区間候補を作る。ラベルは確定した正解ではない。
2. 前後の持続性と特徴から、咳・譜面・椅子・打楽器などの単発音を評価する。
3. 全体の演奏候補から最初と最後を選ぶ。内部の長い空白は作品の終わりにしない。
4. 最後の演奏の後にある拍手を最終拍手の候補とする。後続演奏の疑いがあれば確定しない。
5. 最後の余韻の減衰を追い、安定した暗騒音への移行と拍手の開始を個別に推定する。
6. 拍手の反復を観測してから最初の拍手へ戻る。反復を確認した時刻を最初の拍手としない。
7. 境界候補、競合候補、確からしさと理由を返す。

終止のシンバル、スネアロール、打楽器だけの楽章、非常に弱い終楽章は重点評価対象。ルールで十分な精度が得られなければ小型分類モデルを検討するが、初版の依存条件にはしない。

## 8. 確からしさ・状態・手動補正

### 8.1 確からしさ

開始・終了を別々に `high / medium / low` で評価する。未検証の数値を正解確率として表示しない。

- high: 暗騒音、前後の演奏の文脈、境界特徴が整合し、出力を変える有力な競合候補がない。
- medium: 候補はあるが、拍手・打楽器・弱音等の識別や余韻位置に競合がある。
- low: 演奏範囲や暗騒音が不明瞭で候補を絞れない。

根拠を理由コードと日本語メッセージで返す。実録音で評価するまでhighの判定基準も校正済みとは扱わない。

### 8.2 状態

| 状態 | 意味 | 自動書き出し |
| --- | --- | --- |
| `ready` | 両端high、かつ保留理由なし | 可 |
| `needs_review` | 境界候補または重なり等の確認が必要 | 不可 |
| `no_music` | 演奏候補なし。全無音を含む | 不可 |
| `error` | 不正形式・破損・リソース上限等 | 不可 |

`gain_limited`、メタデータ未転記等は境界の要確認と分けて通知する。全無音と極小音は別に扱い、任意の絶対音量以下をすべて無音としない。

### 8.3 手動補正

開始・終了は個別に上書き可能。全範囲を残す指定も可能。候補をそのまま採用したら `accepted_by_user`、動かしたら `manual_override` として保存する。

no_musicでも、有効な両端を指定すれば手動計画を作れる。不正入力や非有限サンプルは無視できない。片端の手動指定で、もう片端のreviewまで解決したことにしない。

修正後は範囲・フェードを再検証し、対象区間のピークとゲインを再計算する。元の自動解析結果は保持する。別の音源へ計画を適用しないよう、入力全体のSHA-256とサイズを照合する。

## 9. 設定項目

一般向けUIは開始余白、終了余白、ノーマライズON/OFF、境界調整を中心にする。判定閾値は当初開発用とする。

| キー | 既定値 | 有効範囲・役割 |
| --- | --- | --- |
| `pre_roll_ms` | 1000 | 0〜5000 |
| `post_roll_ms` | 200 | 0〜2000。自然な余韻終了後の余白 |
| `applause_guard_ms` | 50 | 0〜500。拍手前の余裕 |
| `fade_in_ms` | 5 | 0〜100。前余白内に限定 |
| `fade_out_ms` | 50 | 0〜500。自然な終了 |
| `applause_fade_out_ms` | 100 | 0〜500。拍手前で切る場合 |
| `normalize` | true | falseなら固定ゲイン1 |
| `target_peak_dbfs` | -1.0 | -12.0〜0.0 |
| `max_gain_db` | 18.0 | 0.0〜36.0。増幅だけの上限 |
| `max_duration_seconds` | 7200 | 0より大きく7200以下。運用上さらに制限可能 |

msは0以上の整数、48フレーム/msで変換する。未知のキー、NaN、範囲外はエラー。設定ファイルよりCLI指定を優先し、最終設定を結果へ記録する。

## 10. Rustの構成と処理契約

| crate | 責務 |
| --- | --- |
| `audio-core` | PCM特徴抽出、候補選択、境界・フェード・ゲイン計算。OS/HTTPに依存しない |
| `audio-wav` | WAV検証、チャンクからのfloat読込、WAV書出し |
| `audio-cli` | ファイル操作、入力照合、進捗・エラー、JSON保存 |
| `audio-wasm` | 同じcore/wavをWASMから利用する薄い窓口 |

マルチスレッドやOSの音声コーデックに依存しない。WASM ABIとRust内部の型は分ける。下記はAPIの意味の契約で、具体的シグネチャは実装時に確定する。

```text
Analyzer.new(audio_info, analysis_config)
Analyzer.push(interleaved_f32_chunk)
Analyzer.finish() -> AnalysisReport
resolve_bounds(report, overrides, trim_config) -> ResolvedBounds
measure_selected_audio(source, bounds, fade_config) -> PeakMeasurement
build_render_plan(bounds, peak_measurement, normalize_config) -> RenderPlan
Renderer.process(chunk, absolute_start_frame, plan) -> output_chunk
```

PCMチャンクの要素数はチャンネル数の倍数で、欠落・重複なく順に供給する。総フレーム数の不一致、finish後のpush、二重finishはエラー。WASMのバッファ所有権・解放方法は窓口側で明記し、生ポインターをJSONへ露出させない。

### 10.1 走査とメモリ

1. 第1走査: WAV検証、入力ハッシュ、全音声の特徴抽出、全体から境界選択。候補周辺は必要に応じて小さく再読込して精査する。
2. 第2走査: 確定範囲を読み、フェード後ピークを測る。
3. 第3走査: フェードと共通ゲインを適用して逐次出力し、実出力ピークを測る。

原本全体をメモリへ置かない。読込チャンクは65,536フレームを初期値とし、任意の正しいチャンクサイズでも結果を同じにする。

120分・ステレオの音声dataは2,764,800,000 bytes。10 msごとに48 bytesの特徴を保存すると約34.56 MB。コアの作業メモリ目標は64 MiB以内とする。設計予算であり、実測確認が必要。時間長に比例する特徴データには上限を設ける。

原本の再読込が必要なAPIとする。初版CLIは通常ファイルを入力とし、seekできない標準入力は未対応にする。

### 10.2 JSON契約

解析レポートと編集計画は別ファイル。双方にschema_version、algorithm_version、入力識別情報、使用設定を持たせる。

| オブジェクト | 必須情報 |
| --- | --- |
| `source` | SHA-256、byte数、48000 Hz、channel数、total_frames、format |
| `analysis` | 状態、境界候補（不明はnull）、境界別confidence、競合候補 |
| `possible_breaks` | 開始・終了フレーム、休止／拍手／不明の手掛かり。正式な楽章番号は付けない |
| `issues` | code、対象境界、severity（info/review）、説明、関連フレーム範囲 |
| `plan` | 確定start/end、適用フェード、共通ゲイン、目標・予想ピーク、確定方法 |
| `render_result` | 出力フレーム数、実出力ピーク、出力SHA-256、通知 |

全PCMや全特徴配列をJSONに含めない。波形プレビューは別データ。schemaのmajorが未知なら拒否し、古い計画を新しい判定ルールで黙って再解釈しない。

## 11. CLI操作案

以下はこれから実装する仕様例であり、現在実行できるコマンドではない。

```sh
amc inspect recording.wav
amc analyze recording.wav --report analysis.json
amc plan recording.wav --analysis analysis.json --out plan.json
amc render recording.wav --plan plan.json --out recording.trimmed.wav

# 試聴して手動補正した場合。秒はフレームへ四捨五入する。
amc plan recording.wav --analysis analysis.json --start 12.345 --end 1240.500 --out plan.json

# 内容確認後に、要確認の候補をそのまま採用する場合。
amc plan recording.wav --analysis analysis.json --accept-review --out plan.json

# 一括実行。readyのときだけ書き出す。
amc auto recording.wav --out recording.trimmed.wav
```

planは未解決のreviewがあれば書出し可能な計画を作らず、候補と理由を表示する。accept-reviewはno_musicの境界を捏造せず、no_musicでは明示した両端を必要とする。

autoは解析JSONを必ず保存し、needs_review/no_musicではWAVを生成しない。成功時は同名ベースのanalysis、plan、render結果を保存する。終了コードは0=完了、2=要確認、3=演奏未検出、1=入力・処理エラー。

進捗と説明はstderr。機械可読出力を選んだ場合はstdoutへJSONのみ出す。処理中断はチャンク境界で受け付ける。出力先と同じディレクトリの一時ファイルへ書き、成功後に確定する。失敗・キャンセルでは今回作った未完成ファイルを消し、既存ファイルを壊さない。

## 12. 将来のWeb画面

操作順は、ファイル選択 → 解析 → 前後の試聴と確認 → 保存。

- 左右波形、残す範囲、演奏開始、余韻終了、最終拍手開始を重ねる。
- 内部の休止候補は薄い目印にし、未確定の楽章名を付けない。
- 冒頭を聴く、末尾を聴く、編集前後を切り替える操作を用意する。初期再生範囲は冒頭5秒・末尾10秒。
- 要確認の箇所と理由を示し、ドラッグ、時刻入力、±10 ms/±100 msで調整できる。
- 表示時刻は原本基準を基本とし、出力後の長さも示す。
- 同じ再生音量で境界を比較するモードと、ノーマライズ効果を聴くモードを用意する。
- 要確認の計画は候補の採用または修正後に保存できる。
- プレビューとWAV保存で同じ境界・フェード・ゲインを使う。再生系で別の自動音量補正を加えない。

## 13. Cloudflare Workersへ接続する際の条件

WorkersでRust/WASMを実行し、コアをCLIと共有する。HTTPとストレージはWorkers層が担当する。

公式資料では、WASMを含むメモリはisolateあたり128 MB、HTTP CPU時間はFreeで10 ms、Paidで既定30秒・最大5分。WASMのスレッドは利用できない。サーバーでの音声処理はPaidを想定して検証し、WASM化だけで上限内に収まるとはみなさない。

48 kHz/32 bit float/ステレオは1分約23.04 MBになるため、通常の録音はR2等に置いた原本を小分けに再読込する構成を想定する。大きなファイルを単一リクエストに丸ごと保持しない。

アップロードは分割・再開可能な方式を候補とし、解析、確認、書出しを別段階にする。Web版の上限はCPU、メモリ、再読込、出力転送の実測から決める。ローカル版120分の上限をそのままWebへ適用しない。

isolateのメモリは同時リクエストで共有されるため処理数も制限する。単一CPU予算を超える場合は、解析状態を保存・再開できる処理分割を別途設計する。非同期化しただけではCPU・メモリ上限は解消しない。

原本は確認後の書出しにも必要。保存期限・削除・再試行はWorkers接続時に定めて画面に表示する。現時点でクラウドリソース作成、認証情報変更、デプロイは行わない。

## 14. エラーと保護動作

| コード | 動作 |
| --- | --- |
| `unsupported_format` | 対応WAV/48 kHz/float32/チャンネルを表示 |
| `invalid_wav` | 破損箇所や矛盾するヘッダーを示す |
| `non_finite_sample` | 最初の該当位置とチャンネルを示す |
| `duration_limit` | 実長と上限を示す |
| `resource_limit` | メモリ等の予算を超える前に停止 |
| `invalid_config` / `invalid_bounds` | 不正なキー・値・範囲を示す |
| `source_mismatch` | 解析・計画の原本と一致しないため停止 |
| `output_exists` | 別名または明示的な上書き指定を求める |
| `io_error` / `cancelled` | 不完全なWAVを完成品として残さない |

CLIは原本のサイズ・更新情報を各走査の前後に確認し、変更があれば中断する。入力をロックできない環境では同時編集しないことを実行契約とする。解析・計画・書出しの間は原本SHA-256で照合する。R2等では同じ原本バージョンを読み続ける契約が必要。

## 15. 受入条件と評価方法

### 15.1 必須の機能条件

- 通常WAVとExtensibleの48 kHz/float32を読み、同じレート・チャンネルのfloat WAVを出す。
- ±1超過を保持して解析し、正規化ONなら目標まで減衰する。
- 無音でNaN・Infinity・異常増幅を発生させない。
- 出力フレーム数が計画と一致し、左右の切断位置・フェード・ゲインが同じ。
- ノーマライズ・フェードともOFFなら、選択範囲のPCMサンプルのビット列が入力と一致する。
- 楽章間の長い無音や拍手を削除・短縮せず、後続楽章を落とさない。
- 余韻と拍手の重なり、後続演奏の曖昧さ、録音の途中切れは要確認となる。
- チャンクサイズを変えても同じ候補・境界・出力になる。
- 全無音や破損入力から自動WAVを生成せず、原本を変更しない。
- 手動で境界を変えたら、その範囲でゲインが再計算される。

### 15.2 数値の一致

同一ビルド・設定で繰り返した結果を再現する。native/WASMは共有の評価音源で境界フレームの一致を要求し、違いが出たら解決する。閾値付近の丸めの差も評価する。

サンプル出力のnative/WASM差は `1e-6 × max(1, abs(reference_sample))` 以下、ピーク差は0.001 dB以内を初期受入基準とする。無音のdB比較はしない。正規化後の実出力ピークは、丸め誤差を含め目標+0.001 dB以下とする。

### 15.3 実録音評価

利用権限のある吹奏楽・アンサンブル録音を初期目標10〜20本用意する。同じ録音だけで閾値を調整せず、調整用と未使用の評価用を分ける。

| ケース | 確認点 |
| --- | --- |
| 弱音・息の音・独奏で開始 | 最初の演奏音を削らない |
| 単発の打楽器で開始 | 持続時間だけで無視しない |
| 曲中の長い休止 | 作品の終わりにしない |
| 2〜4楽章、楽章間に無音または拍手 | 最終楽章まで保持する |
| 弱い終楽章、打楽器だけの区間 | 拍手や雑音として捨てない |
| 長い残響、終止のシンバル | 余韻を早く切らない |
| 拍手が遅い／早い／ない | 各終了規則を守る |
| 余韻に拍手が重なる | 要確認にする |
| 片側が小さい、逆相成分 | 検出漏れや定位変化を起こさない |
| ±1超過、極小音、全無音 | 数値処理と状態が正しい |
| 終演後の咳・椅子・調律・会話 | 最終演奏候補との競合を扱う |

人が最初の演奏音、許容できる終了範囲、最初の最終拍手を付ける。終了の正解は一点ではなく許容区間で持つ。演奏欠落件数、拍手混入件数、許容終了範囲内の件数、自動完了率、要確認率を別々に報告する。

readyを出した評価用録音では、楽章の欠落・演奏本体の切断・明瞭な最終拍手の混入が0件であることをリリース条件とする。全件needs_reviewにして成立させないよう自動完了率も併記する。その数値目標は初回評価後に設定し、未検証の精度を宣言しない。

## 16. 実装の順番

1. WAV検証・チャンク読込、サンプル座標、解析レポート型を作る。
2. 特徴抽出と全体の演奏候補を実装し、複数楽章の内部保持を成立させる。
3. 冒頭・最終余韻・拍手の境界、確からしさ、要確認理由を出し、実録音で調整する。
4. 編集計画、float WAV出力、フェード、共通ノーマライズを実装する。
5. CLIの手動補正、一括実行、JSON保存を整える。
6. WASM窓口を作り、nativeとの一致・速度・メモリを計測する。
7. WorkersとWeb画面を接続し、公式connectorによるデプロイへ進む。

最初の到達点は、実録音1本から作品全体の開始・終了候補と判断理由をJSONで出せること。LTでは波形と前後比較の音で、複数楽章の内部を保ちながら前後だけを整える処理を示す。
